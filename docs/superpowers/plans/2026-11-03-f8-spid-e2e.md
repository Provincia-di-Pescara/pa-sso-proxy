# F8 — Test e2e di login SPID (spid-saml-check)

Spec: §4 F8, decisione §2.3. Obiettivo: un login SPID completo verificato in CI, prerequisito
per valutare l'auto-merge delle librerie SPID/CIE (oggi sempre revisione manuale).

## Ambiente

- `italia/spid-saml-check` (digest fisso) come servizio in un compose override
  `tests/e2e/docker-compose.yaml` sopra lo stack di produzione (stesse immagini della coda
  / della release). Usato come **IdP demo** (`/demo`, utenti di test) e come **validator**
  del metadata SP (`/api/metadata-sp/check` o CLI interna).
- TLS: spid-saml-check espone https con cert self-signed; SATOSA scarica il metadata IdP →
  CA del cert montata nel container satosa (`REQUESTS_CA_BUNDLE`) solo nell'override e2e.
- Nessuna rete esterna: niente demo.spid.gov.it, niente registry AgID (aggregate dal file
  bundled).

## Flusso del test (`scripts/e2e-spid.sh` o pytest+httpx)

1. Stack su volumi vuoti, prima installazione come `smoke-stack.sh` (riuso delle funzioni).
2. WebUI admin: abilita IdP `spid-demo` puntato al metadata di spid-saml-check; client OIDC di
   test (redirect `http://127.0.0.1:<porta>/cb`, PKCE).
3. spid-saml-check scarica il metadata SP dal proxy (`/spidSaml2/metadata`) → validazione
   metadata (fallisce il test su errori AgID).
4. `/OIDC/authorization` (PKCE) → discovery → selezione IdP demo → AuthnRequest a
   spid-saml-check → login utente di test → SAMLResponse POST all'ACS → redirect con `code`
   (cookie `satosa_state` passato a mano: è `Secure`, vedi CLAUDE.md).
5. `/OIDC/token` + `/OIDC/userinfo`: verifica `fiscal_number` e claim attesi; firma id_token
   con il JWKS del proxy.
6. Varianti: scope `legal_entity` (ACS 4, `spid:Purpose=PG`) con utente PG demo; eIDAS non
   testabile (FICEP esterno).

## Quando gira

- PR/coda solo se cambiano `satosa/plugins/**`, `satosa/Dockerfile`,
  `satosa/requirements-runtime.*`, `config-api/app/satosa_config_generator.py` (job
  condizionato con paths-filter fatto a mano su `git diff`, perché il gate richiede run
  `skipped`, non assenti).
- Settimanale su `:latest` (rileva rotture dovute a nuove immagini base/digest).
- In `release.yml` dopo lo smoke stack quando il rebuild tocca satosa (valutare durata).

## Dopo

- Se stabile per ~4 settimane: le PR dependabot/autofix delle librerie SPID (`pysaml2`,
  `satosa`, `pyeudiw`, `cryptojwt`, `cryptography`) possono andare in auto-merge **se** il job
  e2e è nella coda. CIE resta manuale (nessun OP di test locale: valutare un OP CIE mock).

## Rischi

- Form di login di spid-saml-check: HTML che cambia tra versioni → digest fisso e parsing
  minimo (nomi dei campi), test che fallisce in modo esplicito.
- Durata: build + stack + login ~5–8 min; solo coda/settimanale, mai su ogni PR.

## Implementazione (fatta)

- `tests/e2e/docker-compose.yaml` + `tests/e2e/spid_login.py`, attivati da `SMOKE_E2E_SPID=true` in
  `scripts/smoke-stack.sh`; workflow `spid-e2e.yml`.
- Differenze dal piano: TLS non serve (spid-saml-check in HTTP); flusso via `/verifica`
  (client `__spid_verifica__`, PKCE + token + userinfo lato config-api) invece di un client OIDC
  dedicato; validazione strict della AuthnRequest fatta dall'IdP demo stesso (spid-sp-test,
  212 controlli) ad ogni login. Variante persona giuridica non ancora coperta (utente demo PG:
  `montessori`/`leonardo`, serve `legal_entity_enabled`).
- Bug trovati: `/verifica` con solo backend SPID (PR separata), metadata IdP di test mai
  riscaricati dopo cambio URL (documentato in CLAUDE.md, non corretto).
- Verifica locale: stack F6 + fix `/verifica` → `E2E SPID OK`.
